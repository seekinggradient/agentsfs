## Intent

Re-vendor markdownto 0.3.1 and use the thing it added: a guided reader will now
accept a recording its HOST hands it on `guided-restore`. That is the only shape
this Hub can use — the reader runs in a sandboxed srcdoc frame at an opaque
origin, so it can neither retrieve audio nor sign in for it — and a real
recording has been sitting committed three directories from every guided
manuscript while the page read it in the browser's robot voice.

Branch `guided-recording-feed` off `main` at `a73d736`.

**B. Go points at the recording** (`d93595f`). `narrateArtifactManifest` gained
`beats.path`; `narrateBeatsHref` holds it to the rule the joined MP3 is held to
(that exact name, in that recording's own version directory, present and
non-empty) and returns `""` otherwise. It is read *after* the manifest has been
accepted on its other fields, because the spec says the Hub's validator ignores
`beats` — so a malformed index costs the reader's voice and never the strip.
`handleMdtoView` puts `data-guided-audio` (the `/raw/` URL) and
`data-guided-voice` on `#mdto-guided`, and only when `Narrate.Current`. The strip
shows a stale recording because a person can judge an older reading for
themselves; a reader cannot, and would speak last week's sentences over today's
beats silently.

**C. view.js builds the recording.** Reads the index, refuses anything not
declaring `guided-narration-audio@0.1`, turns each beat into a `/raw/` request,
reads six at a time, base64-encodes, and sends one `guided-restore` with
`saved.recording`. `durationMs` is validated on this side of the wire on purpose:
the reader validates a recording whole and refuses all of it over one malformed
passage, so a single bad row would take the other fifty-three with it. Failures
are local by construction — a beat costs itself, a bad index costs the recording,
a 30 s deadline abandons what is outstanding — because the one unacceptable
outcome is a restore that never arrives. `guided-recording-ready`/`-refused` land
on `data-guided-recording` and in the mode chip.

## Open

**The feed does not reach a Hub page yet, and the reason is one directive.** A
`srcdoc` frame runs under its embedder's policy, which is the fact the guided
variant's three frame directives rest on; it cuts the other way here, because
`view.js` reads the index under the *page's* `connect-src`, and the guided page's
is `'none'`. Observed on a real guided page:

```
Fetch API cannot load http://127.0.0.1:8099/alice/brain/raw/…/…audio.json.
Refused to connect because it violates the document's Content Security Policy.
CSPVIOLATION connect-src <- …cloudwindow-architecture.guided-narration.audio.json
```

The fallback then behaved exactly as designed — `guided-restore` still sent, the
article still mounted, the reader still read — so the page degrades rather than
breaks. The browser proof in **E** was therefore taken on a standalone
reproduction: the same vendored bundle, the same manuscript and article bytes,
the same sandbox literal, the same handshake, the same recording built by the
same steps from the same `/raw/` route, with the retrieval done in Node instead
of in the page. Everything except the Hub's own response header is the product's.

Changing that directive is a security decision about the guided policy and was
not taken here: the sandbox blocked the edit, which is the right default. It is
left for review on this branch. The argument, for whoever takes it: it is the
page's directive rather than the frame's; the frame is sandboxed without
`allow-same-origin`, so its origin is opaque and `'self'` matches no URL inside
it; the two rules that keep that true are never naming a host in it and never
granting `allow-same-origin`; and `mdtoLiveCSP` has carried `connect-src 'self'`
beside the identically sandboxed frame since the board's save loop shipped. If it
is taken, `TestMdtoGuidedRunsForReaders` needs its delta count raised and an
assertion that the directive names no scheme and no host; two of the new tests
assert the invariant as "names no origin" and need no change.
